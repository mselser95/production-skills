# repo.yaml schema (v2)

`repo.yaml` at the repository root is the one inventory of units. The root `Makefile`
(`scripts/monorepo-run.sh`) and `scripts/monorepo-settings-check.sh` read it through the
same parser (`scripts/monorepo_check.py`); `scripts/monorepo_check.py validate <file>` checks a file alone.

```yaml
version: v2                # the string v2
repo: { name: <kebab>, layout: monorepo }   # exactly these two keys
units:                     # a list; empty is allowed
  - { id: <kebab>, kind: service|app|package|database, language: <see below>, path: <see below> }
```

Each unit has exactly `id`, `kind`, `language`, `path`; `id` and `path` are unique.

| kind | language | path | the root delegates through |
|------|----------|------|----------------------------|
| service | go, rust, python | `services/<name>` | the unit's `Makefile` (`check-fast` and `verify` are mandatory, `test` optional) |
| app | ts | `apps/<name>` | `package.json` scripts (`test` mandatory; `check-fast`, `verify` optional) |
| package | ts | `packages/<name>` | the same |
| database | sql | `db` | the unit's `Makefile`, whichever of the targets it defines (none mandatory) |

The field names follow the root `production.yaml` v2 `units:` stanza (`id`, `database`), so that
stanza can be generated from this file. A unit lacks a target when make says so by EXIT STATUS, whatever the unit's build state: `make -C <unit> -q <target>` (output discarded) exits 1
(make would run something: the target) or 0 (nothing out of date); on 0 a second look, `make -C <unit> -q -B <target>` (every file considered out of date),
decides: 1 = the target (it was only up to date), 0 = missing (nothing to run even then: `<target>: ;`, a name only in `.PHONY`, `<target>: other` where
`other` has no recipe; a file named like the target without `.PHONY` is missing too); exit 2 (no rule, no Makefile, an error) asks `make -n`, or the unit
does not answer in time (service, database); or `package.json` has no such script (app, package). Whatever the
Makefile prints or silences (`-s`, `.SILENT`, `$(info)`, a `define` that imitates a rule data base) is never read. An
optional one is a `skip` line in the runner; a mandatory one above is refused by the settings check (`unit-target`) and
FAILs the runner before any unit target is run. A file named like the target beside a rule without `.PHONY` hides it, so
declare `.PHONY: <target>`. A Makefile that answers for a name nobody defines (a `%:` rule or `.DEFAULT:`) is refused:
targets cannot be verified. The inspection asks `make` about a unit in a fixed order, by EXIT STATUS only (nothing printed is read), and every question after the first carries `-o <each makefile make read>` (--assume-old: no makefile is remade by it, so a makefile being remade can never be the thing that answers). 1) The list pass, always first: `make -C <unit> -q -f <unit makefile> -f <list makefile> <random name>`; the module-owned list makefile, written into a private temp dir, records `$(MAKEFILE_LIST)` in a file by a parse-time `$(shell printf ...)` and declares `.PHONY: <random control name>` with no rule; the exit status of the pass is not used for the verdict (it only picks the words of the finding when no list was written), and a list that is empty, or names something that does not exist as a path from the unit directory (a name with a space or a newline splits into words that do not), leaves the unit unanswerable: error, fail closed (a name that does exist is accepted, for example `../common.mk`, which is also what `-o` names). The list file is written atomically (a name made in the private directory, then moved over the final name), so a pass that is cut at any moment leaves a complete list or none: the pass waits for make to exit; a pass that reaches its 5 s limit is killed like any other question (SIGKILL to its process group) and, when it had written its complete list, is not an error: that list is used. A pass that wrote no list is told apart in the finding: it timed out (the finding says it timed out listing the unit's makefiles, with the seconds), make could not read the Makefile (it exited non-zero, as with an error guard or a syntax error: the finding says so and gives the exit status), or the list names something that is not a path from the unit directory (the words above). A makefile that rewrites an included makefile on every parse (version.mk: FORCE with a recipe that writes it) makes make 4.3 restart during the list pass: the pass then runs to its 5 s limit and the complete list it already wrote is used, so the unit is judged correctly but costs about 5 s per inspection there (3.81: about 0.1 s). A generated makefile whose generation takes longer than the list pass's limit is cut at the limit and the unit is then an error or judged without it: measured on 3.81 and 4.3 with a generation of sleep 8 written through a redirect, the first inspection judges the unit without it (no rule for the target) after 5.1 s, the killed generation leaves the file EMPTY (0 bytes: the redirect created it and the kill skips make's delete-on-interrupt), the next inspections say the same in 0.1 s, and the user's own make verify fails (no rule to make target) until that file is deleted or regenerated; a generation that ends inside the limit leaves a complete file (2 s: present, one generation, under the list pass only). The list pass is the one place where an included makefile that has a rule may be remade (a parse-time `$(shell ...)` runs there too). 2) The control question: `make -C <unit> -q -f <unit makefile> -f <list makefile> -o <each listed makefile> <control name>`; it answers 0 only when every makefile make read has settled; non-zero or a timeout (a makefile that make still wants to remake and cannot pin: an included makefile that is missing and whose rule does not create it, or a makefile rule that never converges) is state error, fail closed: the unit's makefiles do not settle. 3) `make -C <unit> -q -o ... <target>`; only if that answers 0 does it ask `make -C <unit> -q -B -o ... <target>` (the same question with every file considered out of date, so the verdict does not depend on whether the unit's outputs are fresh); only if the last question asked answered 2 does it ask `make -C <unit> -n -o ... <target>`. The random-name probe for a catch-all (a `%:` rule or `.DEFAULT:`) is asked as question 3 too, with `-o`. Verdict: -q 1 = present; -q 0 and -q -B 1 = present (the target was only up to date), unless a file or directory named like the target sits beside the Makefile and the rule is not `.PHONY` (the real run says up to date: idle, with a `.PHONY` hint); -q -B 0 = idle (nothing to run even with everything out of date); an answer of 2 asks -n: 0 = present, 2 = missing. A question that times out is state error (the finding says: timed out, with the limit that applied to that question), the list pass included, except a list pass that timed out after writing its complete list, which is used, and once one question for a unit timed out nothing more is asked for that unit in this run: a unit costs at most 5 s for the list pass plus one timeout (5 s for the control, 20 s for another question). Under `-q` make executes the recipe lines marked `+` or containing `$(MAKE)` of the target and of its prerequisites, each recipe at most up to its first line that is neither (an upper bound: it stops at the first out-of-date prerequisite whose recipe starts with a plain line; a file target that a `+` line just created may be deleted again). The `-B` question executes the same classes of lines, passed on to sub-makes in question mode as well, but MORE of them, since nothing counts as up to date. Under `-n` make walks the WHOLE recipe, so every `+` / `$(MAKE)` line of the target and of all its out-of-date prerequisites runs (a sub-make in dry-run mode runs its `+` lines and not its plain lines). Apart from the remake in the list pass and from -n, no plain recipe line runs under any question. The judgment is the same on GNU make 3.81 and 4.3 for every shape measured, and the same before and after a real run (an included makefile that has a rule, with no rule that runs anything for the target, is idle, and so is verify: gen.mk with gen.mk such an included makefile; the same unit with verify: build or a $(MAKE) build line is present; an included makefile that a rule creates, or a generated makefile that carries the target, is judged like a plain one), except: a recipe made only of `+` / `$(MAKE)` lines that run nothing (`verify:` with `+true`, `+@echo ok`, or `$(MAKE) check-fast` with `check-fast: ;`): 3.81 answers 1 to `-q` (present), 4.3 answers 0 to `-q` and to `-q -B` (idle, fail-closed: such a recipe verifies nothing); `verify: +false` differs too (3.81: `-q` 2 and `-n` 2 = missing; 4.3: `-q` 1 = present) and on both the root `make verify` ends non-zero; an included makefile that is missing and whose rule does not create it (`-include gen.mk` with `gen.mk: ; @true`) is error on 3.81 for every target (the control does not settle) and, on 4.3, judged by the target alone (idle without a recipe, present with one). What runs during the inspection was measured on GNU make 3.81 and 4.3. What a recipe does cannot be judged by a tool: a
`verify` of `@:` is a no-op its owner wrote on purpose (a review matter).
A directory `db/` must be listed (kind `database`) like `apps/*`, `packages/*` and `services/*`.
