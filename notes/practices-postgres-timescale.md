## 0. Headline facts (all verified on the cited page)
- PG 18 GA 2025-09-25 [S1]. Support: "supports a major version for 5 years"; PG18 final release 2030-11-14, current minor 18.7 [S2].
- PG 19 is ALREADY out (announcement dated 2026-11-19 [S40]); PG 18 is now the previous major. Docker `latest` tag = 19.0 [S20].
  So "PG 18 default" means "pin 18 explicitly, never `latest`". TimescaleDB PG19 support: not found (see UNVERIFIED).
- TimescaleDB officially supports PG 18 from **2.23.0** (GitHub release 2025-10-29 per search result [S4]); matrix: "TimescaleDB 2.23.x through 2.32.x supports PostgreSQL 18" [S5].
  Latest seen: 2.32.1 (2026-11-19). 2.29.0 dropped PG15 [S3].
- TRAP: TimescaleDB 2.32.0 "is compatible only with PostgreSQL versions up to 18.6, 17.11, and 16.15"; 2.32.1 is needed for 18.7+; "every job run by the scheduler fails" on newer minors with older Timescale [S3].
  Gate: the image pin (PG minor x Timescale version) must come from one tested pair; Dependabot-style bump of only one half is a real outage vector.
- postgres_exporter latest 0.21.1 (2026-11-18); CI tests PG 13-18 [S11,S12].
- CIS PostgreSQL 18 Benchmark v1.0.0 exists (CIS May 2026 update) [S41].

## 1. Version and lifecycle
1.1 PRACTICE: run the current minor of PG18. Why: "We recommend that users always run the current minor release associated with their major version." [S2]; "Minor release upgrades do not require a dump and restore" [S2].
    Evidence minor releases matter: 18.2 fixed CVEs incl. CVE-2026-2007 (pg_trgm overflow, "affects only 18.0 and 18.1") [S42].
    Scaffold: image pinned `postgres:18.7-trixie@sha256:<digest>` (tags `18.7`, `18-trixie`, `18.7-alpine` exist [S20]); renovate/dependabot rule groups PG image + timescale image.
    Gate: grep compose/k8s/Dockerfile for `image:` of postgres/timescale; fail if no `@sha256:` digest, or tag is `latest`/`18` floating without digest, or major != declared `DB_MAJOR`.
    Runtime gate: `SHOW server_version_num;` >= pinned minor; `SELECT extversion FROM pg_extension WHERE extname='timescaledb';` equals pinned.
1.2 PRACTICE: official images. `postgres:18*` = plain PG. Timescale: `timescale/timescaledb:latest-pg18` is Alpine, "does not contain TimescaleDB Toolkit or support for PostGIS and Patroni"; `timescale/timescaledb-ha:pg18` is Ubuntu-based, includes Toolkit, PostGIS, Patroni and "offers the most complete TimescaleDB experience" [S6].
    Chainguard hardened/distroless builds exist but need registry auth [S6]. Scaffold default: timescaledb-ha (or light image if no Toolkit need) pinned by digest; never `latest-pg18` unpinned.
1.3 PRACTICE: PG 18 container volume layout changed. "the PGDATA environment variable of the image was changed to be version specific in PostgreSQL 18 and above" -> `/var/lib/postgresql/18/docker`; mount the volume at `/var/lib/postgresql`, not `.../data` [S20].
    Gate: compose lint: for postgres>=18 the volume target must be `/var/lib/postgresql` (a `/data` mount silently loses data across recreate).
1.4 PRACTICE: major upgrade path. "A dump/restore using pg_dumpall or use of pg_upgrade or logical replication is required" [S1].
    `pg_upgrade --check` first, then `--swap`/`--link`/`--clone` for speed; run the NEW binary: "Always run the pg_upgrade binary of the new server, not the old one." [S13]
    PG18 new: statistics are preserved ("Allow pg_upgrade to preserve optimizer statistics", extended statistics NOT) [S1,S13]; afterwards `vacuumdb --all --analyze-in-stages --missing-stats-only` then `--analyze-only` [S13].
    PG18 initdb enables data checksums by default; "pg_upgrade requires matching cluster checksum settings" [S1] (old non-checksum cluster must be converted or init new with `--no-data-checksums`).
    Timescale ordering: update TimescaleDB first, upgrade PG, then update again; "The TimescaleDB version must be the same before and after the PostgreSQL upgrade." [S9] Take a backup: "upgrading is an intrusive operation." [S9]
    Gate (doc/runbook check, not CI-runnable continuously): scaffold ships `docs/db-upgrade.md` and a CI job `upgrade-rehearsal` that restores last backup into N-1 image and runs pg_upgrade --check (Timescale: also ALTER EXTENSION UPDATE).
1.5 MD5 passwords: "Support for MD5 passwords will be removed in a future major version release." [S1] Gate: `SELECT rolname FROM pg_authid WHERE rolpassword LIKE 'md5%'` must be empty.

## 2. Secure configuration baseline
2.1 Authentication = scram-sha-256 only. Why: "provides no protection if an attacker manages to steal the password hash" (md5) vs scram "most secure of the currently provided methods" [S14]. `password_encryption` default is `scram-sha-256`; `md5_password_warnings` default `on` [S15].
    Wiki: don't use `trust` over TCP; "the recommendation being scram-sha-256" [S19]. Docker image: `POSTGRES_HOST_AUTH_METHOD` default scram-sha-256; "It is not recommended to use trust" [S20].
    Scaffold: `pg_hba.conf` mounted explicitly: `hostssl all all <cidr> scram-sha-256`, final `host all all 0.0.0.0/0 reject`. Gate: `SELECT type,database,user_name,address,auth_method FROM pg_hba_file_rules;` fail on any `trust`, `md5`, `password`, or `host` (non-SSL) rule except local socket for the init user; fail if `SHOW password_encryption` != scram-sha-256.
2.2 OAuth (PG18, new): "Add support for the OAuth authentication method." [S1]. Doc: PG is only the resource server; "PostgreSQL does not provide an authorization server"; needs a validator module (`oauth_validator_libraries`), build with OAuth client support; "OAuth should only be used over SSL connections." [S16]
    Verdict: NOT a default for a scaffold (needs external IdP + a validator library; none shipped in core per the page). Offer as opt-in; default stays scram + short-lived per-service creds from a secret manager.
2.3 TLS. Server defaults: `ssl_min_protocol_version` = TLSv1.2 ("satisfies industry best practices as of this writing"); PG18 renamed `ssl_ecdh_curve` -> `ssl_groups` (default `X25519:prime256v1`), new `ssl_tls13_ciphers` [S15].
    Clients: "verify-full is recommended in most security-sensitive environments"; default `prefer` "is not recommended in secure deployments"; only verify-ca/verify-full give MITM protection [S17].
    Scaffold: `ssl=on`, `ssl_min_protocol_version='TLSv1.3'` where all clients allow (else 1.2); DSNs in config templates carry `sslmode=verify-full&sslrootcert=...`; dev compose may use `sslmode=disable` ONLY in a dev profile.
    Rotation: server re-reads cert files on reload; "If a reload finds an error ... the old SSL configuration continues to be used" [S18] -> cert-expiry metric required (section 5).
    Gate: (a) grep all DSN templates for `sslmode=` and fail on `disable|allow|prefer|require` outside dev profile; (b) runtime `SHOW ssl;` = on and `SELECT ssl FROM pg_stat_ssl WHERE pid=pg_backend_pid();` = t for the app role; (c) `SHOW ssl_min_protocol_version`.
2.4 Roles and least privilege. Separate: `owner` (NOLOGIN, owns schema), `migrator` (LOGIN, member of owner, only used in CI/deploy), `app` (DML only), `readonly`, `monitor` (`GRANT pg_monitor`). No superuser for app.
    Predefined roles: pg_monitor "is a member of pg_read_all_settings, pg_read_all_stats and pg_stat_scan_tables" and warns these "grant access to privileged information" [S21].
    Schema hardening: PG15+ default no longer lets everyone CREATE in `public` (DBs upgraded from <=14 keep old behaviour) [S22]; explicit `REVOKE CREATE ON SCHEMA public FROM PUBLIC;` and app tables in a named schema; `ALTER ROLE app SET search_path = app;`. Docs: Default open public path "this is never a secure pattern" [S22].
    Gate SQL: `SELECT rolname FROM pg_roles WHERE rolsuper AND rolname NOT IN ('postgres')` empty for app roles; `SELECT has_schema_privilege('public','public','CREATE')` = f (checks PUBLIC pseudo-role via `has_schema_privilege('app','public','CREATE')` for each role); `SELECT rolname FROM pg_roles WHERE rolbypassrls AND NOT rolsuper` reviewed; app role `NOT rolcreaterole/rolcreatedb`.
2.5 RLS: use only when multi-tenant rows share a table. "If no policy exists for the table, a default-deny policy is used"; owner "is typically not subject" -> use `ALTER TABLE ... FORCE ROW LEVEL SECURITY`; superuser/BYPASSRLS always bypass; RI checks and TRUNCATE are not subject [S23]. App connects as non-owner. Views need `security_invoker` (PG15+ per fetch tool's general knowledge: UNVERIFIED on a primary page).
    Timescale: RLS "not supported on compressed chunks" per search snippet of old API docs [S30, non-primary summary] -> UNVERIFIED for current; test it before relying on RLS + columnstore.
    Gate: `SELECT relname FROM pg_class WHERE relrowsecurity AND NOT relforcerowsecurity` for tenant tables; fail on non-empty.
2.6 SECURITY DEFINER pitfalls: set `search_path` on the function, put `pg_temp` last, `REVOKE ALL ... FROM PUBLIC` then grant selectively, do it in one transaction [S24]. Gate: `SELECT p.oid::regprocedure FROM pg_proc p WHERE prosecdef AND (proconfig IS NULL OR NOT proconfig::text LIKE '%search_path%')` must be empty; plus lint rule in migrations (grep `SECURITY DEFINER` without `SET search_path`).
2.7 Secrets: no passwords in images/migrations/compose. Docker image supports `_FILE` for `POSTGRES_PASSWORD`, `POSTGRES_USER`, `POSTGRES_DB` [S20]. OWASP: "Database credentials should never be stored in the application source code" and "Remove any default accounts and databases." [S31]. Wiki: never `psql -W` [S19].
    Gate: gitleaks/regex over repo for `postgres://user:pass@`; compose uses `*_FILE`/secrets; migrations contain no `PASSWORD '` literal (roles created by bootstrap job with injected secret).
2.8 Network exposure: `listen_addresses` default `localhost` [S15]; compose must not publish 5432 on 0.0.0.0 (use `127.0.0.1:5432:5432`); k8s: NetworkPolicy allow only app/monitor pods. OWASP: "Configuring the database to only bind on localhost." [S31]
2.9 pgaudit: opt-in for regulated services. v18.X "intended to support PostgreSQL 18"; must be in `shared_preload_libraries`; "Audit logging is best-effort and not transactional" [S25]. With Timescale 2.31.0: "pgaudit must come after timescaledb in shared_preload_libraries" (restart) [S3]. Log `pgaudit.log='ddl,role'`, keep `pgaudit.log_parameter=off` unless needed (parameters can contain secrets - inference).
2.10 Data checksums: PG18 initdb default on [S1]; `docker POSTGRES_INITDB_ARGS="--data-checksums"` for <18 [S20]. Gate: `SHOW data_checksums;` = on; alert on `pg_stat_database.checksum_failures` > 0 [S27].
2.11 Encryption at rest: PG has no built-in TDE (UNVERIFIED on primary page); rely on volume/disk encryption + pgBackRest repo encryption (`repo1-cipher-type=aes-256-cbc`, cannot be changed after stanza create) [S26]. Gate: infra-level check (StorageClass encrypted), documented not SQL-checkable.
2.12 Logging without leaking: defaults `log_statement=none`, `log_min_duration_statement=-1`, `log_parameter_max_length=-1` (full) [S28]. Docs: logged statements "may contain sensitive data, including plaintext passwords" [S28].
    Scaffold: `log_min_duration_statement=250ms`, `log_statement='ddl'`, `log_parameter_max_length=0` (no bind values) and `log_parameter_max_length_on_error=0`, `auto_explain.log_parameter_max_length=0` [S28,S29]; `log_connections='receipt,authentication,authorization'` (PG18 list-valued; old `on` still accepted) [S28]; `log_line_prefix='%m [%p] %q%u@%d/%a '`. Gate: `SELECT name,setting FROM pg_settings WHERE name IN (...)` compared to golden file.

## 3. Schema and migrations
3.1 Tool choice. Verified facts: goose runs each file in one transaction, `-- +goose no transaction` needed for `CREATE INDEX CONCURRENTLY`, Down optional [S32]. sqlx: `cargo sqlx prepare --check` for CI [S33]. Alembic: `alembic check` (since 1.9.0) fails when autogenerate would emit ops; cannot detect renames, anonymous constraints [S34]. Atlas: `migrate lint` "Starting with v0.38 ... requires an Atlas Pro plan" [S35].
    RECOMMENDATION: ONE language-neutral mechanism for DDL = plain forward-only SQL files `NNNN_name.sql` in `db/migrations/`, applied by the backend's native runner only as a thin applier (goose for Go, `sqlx migrate` for Rust, Alembic for Python with hand-written ops) - OR one neutral runner (goose binary, plain SQL) invoked by the init/deploy job for all three. Prefer the neutral runner: lint (squawk), drift and Timescale DDL are then identical per language. Do NOT depend on Atlas lint (paid). golang-migrate, refinery, Diesel: not researched (UNVERIFIED).
3.2 Forward-only. Down migrations are untested fiction for data changes; use expand/contract. If a runner offers down, gate may require it only for pure-additive files. (Practice from experience; no primary source.)
3.3 Safe online DDL linter: squawk. Rules verified present [S36]: `require-concurrent-index-creation`, `require-concurrent-index-deletion`, `constraint-missing-not-valid`, `adding-not-nullable-field`, `adding-field-with-default`, `adding-foreign-key-constraint`, `changing-column-type`, `renaming-column/table`, `ban-drop-column/table`, `ban-char-field`, `prefer-text-field`, `prefer-timestamptz`, `prefer-bigint-over-int`, `prefer-identity`, `require-timeout-settings`, `require-lock-timeout`, `require-statement-timeout`, `ban-concurrent-index-creation-in-transaction`, `prefer-robust-stmts`, `ban-drop-database`. Config `.squawk.toml` (`excluded_rules`), CLI `--pg-version`, `--assume-in-transaction`, reporters `tty|gcc|json|gitlab`, docker `ghcr.io/sbdchd/squawk` [S37]. README example pin `v2.74.0` (may be stale).
    Gate: `squawk --pg-version=18 --reporter=json db/migrations/*.sql` on changed files. Squawk is Postgres-generic: it does not know hypertable/columnstore DDL (UNVERIFIED how it treats `WITH (timescaledb.*)`; the gate must allow-list and test it with a fixture).
3.4 Lock/timeout hygiene in every migration: first lines `SET lock_timeout='5s'; SET statement_timeout='60s';` (`lock_timeout` default 0 = infinite wait; "Setting it at or above a nonzero statement_timeout has no useful effect") [S38]. Run migrator role with these set at role level.
    Patterns (standard PG practice; docs not fetched, UNVERIFIED on primary page): `CREATE INDEX CONCURRENTLY` (no txn); `ADD CONSTRAINT ... NOT VALID` then `VALIDATE CONSTRAINT`; NOT NULL via validated CHECK first; avoid table rewrites (type change, volatile default on old PG).
3.5 Types (wiki "Don't Do This" [S19]): `timestamptz` ("use timestamptz ... instead"), `text` over `char(n)`, `numeric` over `money` ("Numeric, or (rarely) integer may be better"), identity over `serial` ("For new applications, identity columns should be used instead"), lowercase snake names, half-open ranges instead of BETWEEN, `NOT EXISTS` over `NOT IN`. Money: `numeric(p,s)`, never float (project rule; repo CLAUDE standard is string-decimal on the wire).
    Gate: after migrations, `SELECT table_name,column_name,data_type FROM information_schema.columns WHERE table_schema='app' AND data_type IN ('timestamp without time zone','money','real','double precision','character')` must be empty (allow-list file for exceptions).
3.6 UUIDs: PG18 `uuidv7()` "temporally sortable" [S1,S39]; `uuid_extract_timestamp` works for v1/v7, "not necessarily exactly equal to the time the UUID was generated" [S39]. Use `DEFAULT uuidv7()` for new PKs (index locality); `gen_random_uuid()`/`uuidv4()` has no ordering. Do not expose it as an authority on creation time. Monotonicity within a session is NOT stated on the page.
    Hypertable note: a UUID PK cannot satisfy the "unique index must include time" rule alone (see 6.3).
3.7 Generated columns: PG18 default is VIRTUAL; "must not reference user-defined functions or types"; logical replication of generated columns "currently only supported for stored" [S43]. Scaffold: be explicit (`STORED` or `VIRTUAL`) in DDL; Timescale partition column cannot be generated [S10-limits].
3.8 Constraints are the source of truth: NOT NULL, CHECK, FK, UNIQUE in DDL, not in app only. Name every constraint (Alembic cannot detect anonymous ones [S34]). Enums vs lookup: prefer lookup/CHECK for evolving sets (squawk has `require-enum-value-ordering`, `ban-add-enum-value` [S36]).
3.9 Drift detection: Alembic `alembic check` [S34]; neutral approach = CI job applies migrations to empty PG18 and dumps `pg_dump --schema-only`, compared against committed `db/schema.sql` snapshot. Verified-by-docs part: `pg_dump` exists; the exact diffing is scaffold work.
3.10 Idempotency: migration runner tracks versions; scaffold's init job is re-runnable (`CREATE ... IF NOT EXISTS` only for bootstrap objects). squawk `prefer-robust-stmts` [S36].

## 4. Query access
4.1 Parameterised only: OWASP "SQL Injection is best prevented through the use of parameterized queries" and "query parameterization is done server-side!" [S44]. Identifier allow-listing is NOT covered by that page (UNVERIFIED primary). Gate: semgrep/grep for string-built SQL (`fmt.Sprintf("SELECT`, `format!("SELECT`, f-strings with SELECT) failing CI.
4.2 Typed generation: sqlc Go is Stable for PostgreSQL; Kotlin/Python/TypeScript plugins Beta; Rust only via community `sqlc-gen-sqlx` (Beta); a community Python plugin `sqlc-gen-better-python` listed Stable [S45]. Rust: `sqlx::query!` checks at build time against `DATABASE_URL`, offline `.sqlx` committed, `cargo sqlx prepare --check` in CI [S33]. Python: SQLAlchemy 2 / psycopg 3 / asyncpg not researched (UNVERIFIED) - recommend psycopg 3 + typed row factories as default.
    Gate: `sqlc diff` (Go) / `cargo sqlx prepare --check` (Rust); Python: mypy + a test that runs every named query against the migrated container.
4.3 Pooling and PgBouncer: `pool_mode` default session; `default_pool_size` 20; `query_wait_timeout` 120s; transaction pooling prepared statements work via `max_prepared_statements` (default 200; 0 disables) but SQL-level PREPARE/EXECUTE "are forwarded straight to PostgreSQL and are not tracked"; `server_reset_query` not used in transaction mode [S46]. Session features (advisory locks, SET, LISTEN) unreliable in transaction mode [S46].
    `SHOW POOLS/STATS` column names: page does not document them (UNVERIFIED). pgcat / PG built-in pooling: not researched; PG has no built-in pooler (general knowledge, UNVERIFIED).
    Scaffold: app-side pool max = (max_connections - reserved) / replicas, `max_connections` default 100 [S15]; pool acquire timeout, connect timeout, `application_name` set per service (feeds `pg_stat_activity.application_name`, `%a` in log prefix).
4.4 Timeouts per role (defaults all 0 = off [S38]): `ALTER ROLE app SET statement_timeout='30s', lock_timeout='2s', idle_in_transaction_session_timeout='60s'`; docs advise setting per role/db/session not in postgresql.conf [S38]. `idle_session_timeout`: "Be wary of enforcing this timeout on connections made through connection-pooling software" [S38]. `transaction_timeout` exists (PG17+) [S38].
    Gate: `SELECT rolname, rolconfig FROM pg_roles WHERE rolname IN ('app')` must contain the three settings.
4.5 Isolation + retry: default read committed [S38]. "applications must be prepared to retry transactions that fail due to serialization errors" (SQLSTATE 40001); deadlock 40P01 "may also be advisable to retry"; retry the WHOLE transaction; unique-key (23505)/exclusion (23P01) only selectively [S47]. Scaffold ships a `with_retry` helper per language (jittered backoff, max attempts) and a test that forces 40001 with two concurrent SERIALIZABLE txns.
4.6 Queue/outbox: `FOR UPDATE SKIP LOCKED` is for "queue-like table" consumers; "Skipping locked rows provides an inconsistent view of the data, so this is not suitable for general purpose work." [S48]. Outbox: write event row in the same transaction as the state change; relay with SKIP LOCKED. Idempotency keys: UNIQUE constraint + `INSERT ... ON CONFLICT DO NOTHING` (note Timescale: upserts that move rows between chunks unsupported, unique index must include time [S10-limits]). Advisory locks break under PgBouncer transaction mode [S46].
4.7 N+1 detection: `pg_stat_statements` `calls` per `queryid` vs request count; test asserts max N queries per request (app-level query counter); not a PG-native feature.

## 5. Observability - born with probing and metrics (core requirement)
5.1 Probes.
    - Liveness of the DB container: `pg_isready -h localhost -p 5432 -t 3` exit 0 = accepting; 1 = rejecting (startup); 2 = no response; 3 = no attempt [S49]. It does NOT verify credentials: "It is not necessary to supply correct user name, password, or database name" [S49]; so it is a container liveness/healthcheck only.
    - App readiness for the DB dependency: a real query with timeout through the real pool, as the app role: `SELECT 1` plus (optional) a canary `SELECT count(*) FROM app.schema_migrations` check that the expected migration version == code's version. Timeout <= 2s via `statement_timeout`/context deadline. Readiness must NOT flap on replica lag unless the service reads from replicas: lag-aware readiness = `SELECT EXTRACT(EPOCH FROM now()-pg_last_xact_replay_timestamp())` on the replica `< threshold` (standard function; docs for it not fetched, UNVERIFIED on primary page).
    - Liveness of the app must not depend on the DB (avoid restart storms).
    - Compose healthcheck: `pg_isready -U $POSTGRES_USER -d $POSTGRES_DB`; PG image page has no healthcheck advice (UNVERIFIED).
5.2 Monitoring role: `CREATE ROLE monitor LOGIN PASSWORD ... ; GRANT pg_monitor TO monitor; GRANT CONNECT ON DATABASE app TO monitor;` exactly what postgres_exporter documents ("grant the pg_monitor role" PG10+, plus CONNECT) [S12]. OTel receiver: `SELECT on pg_stat_database` minimum, `pg_monitor` for query samples, `pg_stat_statements` in `connect_database` for top queries [S50]. Timescale views `timescaledb_information.*` are readable by any role (UNVERIFIED), test it.
    Gate: monitor role exists, `NOT rolsuper`, member of pg_monitor only, `rolconnlimit` set (e.g. 3), `pg_hba` restricts it.
5.3 Exporter recommendation: postgres_exporter (prometheus-community) as the default sidecar/container: actively released (0.21.1, 2026-11-18), PG 13-18 in CI [S11,S12]. Default-ON collectors: database, locks, replication, replication_slots, settings, stat_activity, stat_archiver, stat_bgwriter, stat_database, stat_progress_vacuum, stat_replication, stat_user_tables, statio_user_tables, wal. Default-OFF: database_wraparound, long_running_transactions, postmaster, process_idle, stat_activity_autovacuum, stat_checkpointer, stat_statements, stat_wal_receiver, statio_user_indexes, xlog_location [S12].
    Scaffold flags: `--collector.stat_statements --collector.stat_checkpointer --collector.database_wraparound --collector.long_running_transactions --collector.stat_activity_autovacuum --collector.statio_user_indexes`; `--collector.stat_statements.limit=100`, keep `include_query` off (default off, `query_length` 120) to avoid leaking SQL [S12]. Note PG17+ moved checkpoint stats to `pg_stat_checkpointer`, and PG18 moved WAL timing to `pg_stat_io` [S1,S27], so `stat_checkpointer` must be enabled and `stat_bgwriter` checkpoint columns are gone (exporter handling of each: UNVERIFIED).
    Lifecycle hazards (verified): `--auto-discover-databases` and `--extend.query-path` marked deprecated; custom queries file path deprecated "in favor of built-in collector functions" [S12]; 0.20.0 renamed `replication_slot` -> `replication_slots` and renamed `pg_replication_slot_*` metrics -> `pg_replication_slots_*`, removed `--disable-settings-metrics` [S11]; 0.21.0: counters wrap at 2^53 ("one-time false rate() spike"), `--web.max-requests` default 40 -> 503, deprecated env vars removed in v0.22.0, "A collector that fails partway through a scrape now has all its metrics dropped" [S11]. => pin exporter version, test after every bump (5.6).
    Alternatives: OTel Collector `postgresqlreceiver`: metrics stability beta, logs development; required `username` + `password` or `db_auth`; default `collection_interval` 10s; `databases` default all non-template; TLS block; metric name list not on the README page (UNVERIFIED names) [S50]. pgwatch: not researched (UNVERIFIED). RECOMMENDATION: postgres_exporter as default (stable names, wide dashboards); OTel receiver as opt-in when the service already ships an OTel Collector. CNPG has a built-in exporter on :9187 with `cnpg_collector_*`/`cnpg_pg_*` metrics [S51] (detail UNVERIFIED).
5.4 Server settings at init (all are real PG settings; defaults verified where marked):
    - `shared_preload_libraries='pg_stat_statements'` (+ `timescaledb` first; `pgaudit` after it [S3]); `compute_query_id=on` (auto also activates it) [S27a]; `pg_stat_statements.max=10000` (default 5000), `.track=top` (default top; `all` includes nested), `.track_planning=off` ("may incur a noticeable performance penalty"), `CREATE EXTENSION pg_stat_statements` in each DB; view `pg_stat_statements_info.dealloc` shows eviction pressure; `queryid` "not stable across major versions" [S27a].
    - `track_io_timing=on`; PG18: `track_wal_io_timing` now feeds `pg_stat_io` (object='wal'), removing `wal_write/wal_sync(_time)` from `pg_stat_wal` [S1,S27]. Overhead of these timers: not on fetched pages (UNVERIFIED); run pg_test_timing in scaffold doc.
    - `auto_explain` via `session_preload_libraries`; `log_min_duration='3s'`, `log_analyze=off` (default; analyze "can have an extremely negative impact on performance" when per-node timing on), `sample_rate`, `log_parameter_max_length=0` [S29].
    - `log_lock_waits=on` (default off), `log_autovacuum_min_duration=10min` default (set to `1min`), `log_checkpoints=on` (default on), `log_temp_files=0` (default -1), `log_min_duration_statement=250ms`, `log_connections` list-valued in PG18 [S28].
    Gate: `SELECT name,setting FROM pg_settings WHERE name IN ('compute_query_id','track_io_timing','log_lock_waits','log_temp_files','log_autovacuum_min_duration','log_checkpoints','track_activity_query_size','shared_preload_libraries')` equals golden; `SELECT count(*) FROM pg_stat_statements` runs without error.
5.5 MUST-HAVE metric set. SQL = verified view/column (PG18 docs [S27]); `exporter series` names are the exporter's usual naming and are UNVERIFIED (the 5.6 test must scrape and pin the actual names per version).

## 6. TimescaleDB design rules
6.1 Licensing and self-hosting: repo LICENSE: code outside `tsl/` is Apache-2.0; `tsl/` is the Timescale License; "binaries with -tsl in their name fall under the Timescale License" [S7]. Editions doc: Apache-2 edition has core hypertable functions (`create_hypertable`, `drop_chunks`, `show_chunks`); Community edition adds columnstore/Hypercore, continuous aggregates, policies (retention, columnstore, reorder, cagg), `add_job`, SkipScan, gap-fill etc. [S8]. Search snippet (non-primary forum): Apache build rejects `add_continuous_aggregate_policy`/`add_retention_policy` [S58]. Free to self-host Community "as long as you are not offering TimescaleDB as a hosted DBaaS" (search summary of Tiger license page, [S59]).
    Gate: `SHOW timescaledb.license;` must be `timescale` (not `apache`) when the service uses caggs/compression/retention. Managed Postgres that only ships the Apache edition (e.g. many hyperscaler offerings; provider list UNVERIFIED) cannot run compression/caggs/policies: the scaffold must pick self-hosted/CNPG/Tiger Cloud for Timescale services.
6.2 Creation syntax (current): `CREATE TABLE ... WITH (timescaledb.hypertable, timescaledb.partition_column='time')`; partition column auto-detected from the first `timestamptz`; explicit `partition_column` needed if none or several; default chunk interval 7 days via `timescaledb.chunk_interval`; "all active chunks fit in memory" sizing rule; existing tables use `create_hypertable(..., migrate_data => true)` [S60]. Cagg syntax: `CREATE MATERIALIZED VIEW ... WITH (timescaledb.continuous) AS ...` (`WITH NO DATA` to skip initial fill) [S61]. Doc also shows `WITH (tsdb.hypertable)` alias [S61]; use `timescaledb.` prefix as the first page does.
    With the new syntax "Creating a hypertable ... enables hypercore by default" and "TimescaleDB creates a columnstore policy automatically, with after set to the chunk interval" [S62] - a scaffold must state columnstore defaults explicitly (segmentby/orderby) instead of relying on this.
6.3 When a table should be a hypertable: append-mostly rows keyed by time, queried by time range, with retention/rollup needs, and large enough that chunking pays (rule of thumb, no primary source). NOT for: small reference tables, rows updated by non-time keys, tables needing FKs to other hypertables ("Foreign keys from one hypertable to another hypertable are not supported" [S10]), or UUID-only PKs.
    Constraints: "a unique index must contain all the partitioning columns"; "You cannot create a unique index without time" [S63]; PK includes `time` -> `PRIMARY KEY (device_id, time)`. UPDATEs that move rows between chunks and `INSERT ... ON CONFLICT UPDATE` upserts "unsupported" per limitations page [S10] (exact scope: UNVERIFIED, the page lists them under moving rows across partitions). Time column cannot be NULL or generated [S10]. Table inheritance not supported [S10].
    Gate: for each hypertable (`timescaledb_information.hypertables`): PK/unique indexes include the partition column; time column `timestamptz NOT NULL`.
6.4 Chunk interval: default 7 days [S60]; "all active chunks fit in memory"; high ingest -> shorter (e.g. 1 day) [S60]; `set_chunk_time_interval` applies only to NEW chunks; "time intervals on existing chunks are not changed", transition chunks can be smaller [S64]. Specific "25% of memory" rule not found on current pages (UNVERIFIED). Gate: count chunks per hypertable (`SELECT hypertable_name,count(*) FROM timescaledb_information.chunks GROUP BY 1`) stays < alert (e.g. 10k); chunk size p50 sane.
6.5 Space partitioning: current docs only say "optionally add a secondary space-partitioning dimension in Tiger Console" [S60]; whether still recommended: UNVERIFIED. Default: time-only.
6.6 Columnstore (compression): `ALTER TABLE ... SET (timescaledb.enable_columnstore, timescaledb.segmentby=..., timescaledb.orderby=...)`; settings "apply to chunks that have not yet been converted"; `add_columnstore_policy(..., after => INTERVAL '7d')`; policy job "single-threaded"; remove+add policy to change `after`; hypercore supports INSERT/UPDATE/DELETE/UPSERT on compressed data; backfill recipe: `alter_job(<id>, scheduled => false)`, backfill, convert chunks, re-enable [S62]. 2.29.0 added `recompress_unordered` policy option [S3]. 2.32.0 uses Adaptive Integer Compressor (opt-out `timescaledb.enable_aic_compression=off`) [S65]. "each compressed batch holds 1,000 rows" -> tiny chunks compress badly [S66].
    segmentby/orderby selection guidance: current page has no rules beyond "tune" (UNVERIFIED); heuristic: segmentby = equality-filter low/medium-cardinality id (device_id); orderby = time DESC.
    Terminology: docs now say "columnstore" not "compression"; `hypertable_compression_stats` deprecated [S57]; compression-policy `proc_name` stays `policy_compression` [S54]. 
6.7 Continuous aggregates: real-time aggregation is OFF by default since 2.13 ("real-time aggregates are DISABLED by default") [S61]; hierarchical caggs supported; LEFT/LATERAL JOIN need >=2.16; "Changes to standard PostgreSQL table are not tracked" [S61]; pre-2.7 non-finalized caggs block upgrade to 2.25 [S61]. Refresh policy: `start_offset`, `end_offset`, `schedule_interval` (default 24h); keep `end_offset` outside the current bucket; `NULL start_offset` makes deletions propagate (so with a retention policy dropping raw data, set a finite `start_offset` or the cagg loses history); backfills outside refresh window need a second policy or manual `CALL refresh_continuous_aggregate(...)`; avoid NULL bounds on manual refresh [S67]. 2.30.2 renamed granular refresh options to `timescaledb.cagg_granular_refresh_*` [S3].
    Gate: for every cagg, a refresh policy job exists (`timescaledb_information.jobs WHERE proc_name='policy_refresh_continuous_aggregate'`) and retention `drop_after` > cagg `start_offset`.
6.8 Retention: `add_retention_policy('t', INTERVAL '...')` "drop[s] entire chunks once their time range falls outside your window"; cannot drop future chunks automatically [S68]. `drop_created_before` / cagg interaction: UNVERIFIED on that page. Gate: each hypertable has a retention policy or an explicit `retention: forever` annotation in `db/timescale.yaml`.
6.9 Out-of-order data: allowed in rowstore and columnstore; costs: invalidation of cagg refresh windows and recompression (see backfill recipe [S62,S67]).
6.10 DDL on hypertables / compressed chunks: current docs fetched do not list restrictions (UNVERIFIED); search snippet of old docs: schema changes on compressed hypertables only from 2.1, update/delete on compressed from 2.11 [S30, non-primary]. 2.31.0: "Block ALTER and DROP operations on a granular-refresh tracking column" [S3]. Gate: migration tests (section 8) must run each DDL against a hypertable with compressed chunks.
6.11 Backup/restore: pg_dump/pg_restore works with compressed hypertables; sequence: `CREATE EXTENSION timescaledb` on target, `SELECT timescaledb_pre_restore();`, `pg_restore -Fc`, `SELECT timescaledb_post_restore();`; DO NOT use `pg_restore -j` ("does not correctly restore the TimescaleDB catalogs"); dumping individual tables with pg_dump flags "lacks necessary information" [S69]. Record PG + Timescale versions with every backup [S69]. Restore target needs the same (or newer, ordered upgrade) Timescale version [S9,S69]. PITR via pgBackRest/physical is the primary DR path.
6.12 Extension upgrade: `psql -X -c "ALTER EXTENSION timescaledb UPDATE TO '<v>'"`, verify with `\dx timescaledb`; "Best practice is to always use the latest version" [S9]. Loader changes (2.31/2.32) "require a restart"; 2.32.0: background scheduler now runs "as the database owner instead of as superuser" [S3] -> the owner role must be able to run policy jobs; test it.
6.13 Logical replication/CDC: not verified from a primary page. Search snippets (non-primary, ClickHouse blog): hypertables "don't support publish_via_partition_root" [S70]; PG18 itself replicates only stored generated columns [S43]. Scaffold default: do not plan CDC from hypertables; use outbox table (plain table) for events.
6.14 Tuning: `timescaledb-tune` reads postgresql.conf and recommends memory/parallelism/WAL ("--memory", "--cpus", "--dry-run", "--yes"); repo shows 155 commits and no visible releases in the fetched page (maintenance status UNVERIFIED) [S71]. In containers pass explicit `--memory/--cpus` equal to cgroup limits or set GUCs yourself (container limits not auto-detected: UNVERIFIED).

## 7. Reliability and operations
7.1 Backups: PITR = `wal_level>=replica`, `archive_mode=on`, `archive_command` that returns 0 "if and only if it succeeds" and "refuse to overwrite existing files"; failed archiving fills `pg_wal`: "PostgreSQL will do a PANIC shutdown" [S72]. `pg_dump` "can't be used for continuous archiving" [S72]. pgBackRest 2.60.1: `archive-push`, `stanza-create`, `check`, full/diff/incr, `--delta` restore, PITR `--type=time --target=...`, client-side AES-256 repo encryption [S26]. Barman / WAL-G comparison: NOT researched (UNVERIFIED). Recommendation: pgBackRest (or CNPG's built-in barman-cloud integration - UNVERIFIED) with `check` as a gate.
    Gate: `SHOW archive_mode`=on, `SHOW archive_command`/`archive_library` non-empty; `pg_stat_archiver.failed_count` flat after forced `pg_switch_wal()`; `pgbackrest check` exits 0.
7.2 Restore test as a gate: scheduled job restores latest backup into a scratch instance, runs `SELECT count(*)` smoke + migration-version check + (Timescale) `timescaledb_information.job_stats` sanity, emits `restore_test_last_success_timestamp` (5.5). Docs: "Inspect the contents of the database to ensure you have recovered to the desired state" and "consider keeping several backup sets" [S72]. Negative proof: corrupt the backup path -> job RED.
7.3 HA: Patroni (bundled in timescaledb-ha image [S6]); CloudNativePG operator: docs moved to cloudnative-pg.io/docs/current; supported PG versions and Timescale support not extractable (UNVERIFIED). CNPG exposes metrics on 9187 [S51].
7.4 Autovacuum: PG18 caps the vacuum threshold for huge tables: threshold = Minimum(`autovacuum_vacuum_max_threshold`, base + scale_factor*tuples) [S52]; eager freezing tunable via `vacuum_max_eager_freeze_failure_rate` [S52]; `autovacuum_freeze_max_age` default 200M [S52]; default `log_autovacuum_min_duration` 10min [S28]. Starting points (practice, no primary source): lower `autovacuum_vacuum_scale_factor` to 0.05 on large tables via per-table storage params; hypertable chunks are separate tables -> autovacuum applies per chunk.
7.5 Resources in containers: `shared_buffers` default 128MB; starting point "25% of system memory" on a dedicated server, >40% "unlikely" to help [S73]; `max_connections` 100 [S15]; `huge_pages=try` default; transparent huge pages "discouraged" [S73]. Set `shm_size` for docker and a memory limit; derive values from limits, never from host RAM.
7.6 PG18 I/O: `io_method` default `worker` (alternatives `io_uring` needs a build with liburing, `sync`); `io_workers` 3; `effective_io_concurrency` and `maintenance_io_concurrency` default 16 [S73,S1]; `io_method` "can only be set at server start" [S73]. Guidance: keep `worker`; benchmark `io_uring` only on custom builds (the official docker image's liburing build status: UNVERIFIED); watch `pg_stat_io` and AIO wait events [S27].
